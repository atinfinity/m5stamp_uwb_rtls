# 構成カスタマイズガイド(アンカー・タグの台数と配置)

アンカー/タグの台数変更・アンカー配置の変更手順。**測位系の構成情報は
`server/config.yaml` に一元化**されており、サーバー・シミュレータ・仮想タグ・
リプレイはすべてここから追従する。ファームウェアに入るのは自ノードのアドレスだけ。

物理的な配置の設計指針(高さ・DOP・アンテナ取り回し)は基本設計
[rtls-design.md](rtls-design.md) §3.3、アドレス体系は §4.2 を参照。

## 1. 座標系

- フロア左下が原点 (0, 0)、x 右・y 上、単位 [m]
- `floor.width_m` / `floor.height_m` がフロア寸法。セル矩形・アンカー座標はこの範囲内であること(起動時に検証され、不備は起動失敗になる)

## 2. アンカーを追加・移動する

`server/config.yaml` の 2 箇所を編集する:

```yaml
anchors:
  "0x0019": { x: 12.5, y: 50.0, z: 2.2, bias_mm: 0 }   # ① 追加 (実測座標を登録)
cells:
  C: { rect: [0, 25, 25, 50], anchors: ["0x0013", "0x0014", "0x0016", "0x0017", "0x0019"] }  # ② 担当セルへ組み込み
```

- **アドレス**: `0x0010`〜 の連番を使う(体系上 12 台 = `0x001B` まで。C++ ソルバーのテーブル上限は 16)
- **座標**: レーザー距離計で測量した実座標(±3 cm 目標)。`z` はアンカー高さ
- **bias_mm**: 校正オフセット(Step 1 の実測で決定。未校正なら 0)
- **セルへの登録**: アンカーは `cells` のどこかに入れて初めて測距に使われる。1 セル 4〜6 台、
  最低 3 台(3 台未満のセルは解算不可)。同じアンカーを複数セルで共有してよい
- 起動時検証: セルが未知のアンカーを参照 / 矩形がフロア外 / アドレス重複はエラーで起動しない

**ファームウェア側**: アンカー FW は自分のアドレスを知っているだけでよい。
1 台ごとに `firmware/anchor/platformio.ini` の `-DNODE_ADDR=0x00XX` を書き換えて書き込む。

反映: サーバーを再起動するだけ。タグへの担当アンカー通知(ハンドオーバー)は
サーバーが retained メッセージで自動配信する。

## 3. セル(分割)を変更する

- セルは軸平行矩形 + 担当アンカーリスト。フロア全域がどこかのセルに入るようにする
  (どのセルにも入らない座標は最近傍セルで補われるが、精度は落ちる)
- セル寸法の目安は 15〜25 m 四方(基本設計 §3.3)。境界のハンドオーバーには
  `tuning.handover_margin_m`(既定 2 m)のヒステリシスが効く

小規模構成(1 セル・アンカー 4 台)の例:

```yaml
floor: { width_m: 10.0, height_m: 10.0, tag_height_m: 1.0 }
anchors:
  "0x0010": { x: 0.0,  y: 0.0,  z: 2.0, bias_mm: 0 }
  "0x0011": { x: 10.0, y: 0.0,  z: 2.0, bias_mm: 0 }
  "0x0012": { x: 0.0,  y: 10.0, z: 2.0, bias_mm: 0 }
  "0x0013": { x: 10.0, y: 10.0, z: 2.0, bias_mm: 0 }
cells:
  A: { rect: [0, 0, 10, 10], anchors: ["0x0010", "0x0011", "0x0012", "0x0013"] }
tags: ["0x0001"]
```

## 4. タグを追加する

1. `config.yaml` の `tags` にアドレスを追加(`"0x0001"`〜`"0x0005"`)
2. タグ FW を 1 台ごとに `-DNODE_ADDR=0x000X` でビルド・書き込み
   (`firmware/tag/platformio.ini`)

**5 台が現行 TDMA 設計の上限**。スロット割当はアドレスから自動で決まり
(`firmware/lib/rtls_common/rtls_slots.h`: スーパーフレーム 500 ms ÷ スロット 100 ms)、
タグを増やすには次のいずれかが必要:

- スーパーフレームを伸ばす(`kSuperframeMs` を 1000 ms に → 10 台 × 1 Hz)
- スロットを詰める(Step 1 実測で交換時間を確認してから)
- SS-TWR 化([ss-twr-design.md](ss-twr-design.md) — 8 台 × 2 Hz 相当)

逆にタグが 2〜3 台なら `kSlotPeriodMs` を 150〜200 ms に広げて更新レートを上げられる
(基本設計 §4.4)。**スロット定数を変えたら全タグを再書き込みし、
`firmware/test_native/run.sh` のスロットテストも更新する。**

## 5. 動作確認(実機レス)

変更後は仮想タグでそのまま検証できる(シミュレータは config の
タグ数・アンカー・セルに自動追従する):

```bash
uv run pytest tests/test_e2e_replay.py -s   # 変更後の構成で CEP を確認
uv run python -m server.app &               # + mosquitto + tools/virtual_tag.py
```

UI(http://localhost:8000)でアンカー配置とセル境界が意図どおりかを目視確認し、
アンカー監視パネルで全アンカーの測距が流れていることを確認する。

## 6. よくある失敗

| 症状 | 原因 |
|---|---|
| サーバーが起動しない(ValidationError) | セルが未登録アンカーを参照 / 矩形がフロア外 / アドレス重複 |
| 特定エリアで COASTING が多発 | そのセルの見通しアンカーが 3 台未満になっている。アンカー追加か配置変更 |
| セル境界で位置が飛ぶ | 隣接セルとアンカーを共有していない(基本設計 §3.3 の共有配置にする) |
| 新タグの位置が出ない | `tags` への追加漏れ(サーバーは未知タグの ranges を破棄する)、または FW の `NODE_ADDR` 重複 |
